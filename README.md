# Аким на 5 часов · AI Urban Strategy Copilot

Учебный симулятор городских решений для HackAlem. Выберите пять мероприятий, распределите бюджет, сравните последствия или найдите сценарий под свою цель.

**Числа считает Python. Один AI Supervisor выбирает инструменты и объясняет рассчитанные результаты.** Все показатели синтетические: это не статистика и не прогноз развития Астаны.

## Что работает

- Обзор пяти районов, исходные показатели и слабые места.
- Ручной выбор пяти мер с назначением районов, проверкой бюджета и всех ограничений.
- Расчёт на восемь кварталов: эффекты, синергии, показатели, Score, вклад мер и графики.
- Полный детерминированный поиск по четырём целям и сравнение двух планов.
- Один Supervisor с пятью tools и структурированным ответом с источниками расчётов.
- Без ключа доступны все расчёты, поиск и сравнение; AI честно сообщает о недоступности.

## Запуск

Требуются Python 3.12 и Node.js 22.13+ (используется Vite 6). Команды ниже выполняются из корня репозитория в PowerShell.

```powershell
py -3.12 -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.lock.txt
npm.cmd --prefix frontend ci
npm.cmd --prefix frontend run build
.venv/Scripts/python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Откройте **http://127.0.0.1:8000**. FastAPI раздаёт собранный frontend. Документация API: **http://127.0.0.1:8000/docs**. После новой сборки перезапустите backend, если папки `frontend/dist` ещё не было при старте.

В Linux/macOS используйте `python3.12`, `.venv/bin/python` и `npm` вместо Windows-вариантов команд.

Для разработки запустите backend как выше, а во втором терминале:

```powershell
npm.cmd --prefix frontend run dev
```

Dev-интерфейс: **http://127.0.0.1:5173**. Vite проксирует `/api` на backend. База данных, Docker и внешние городские сервисы не нужны.

`requirements.txt` задаёт допустимые версии; `requirements.lock.txt` и `frontend/package-lock.json` фиксируют проверенный набор зависимостей.

## LLM — необязательная настройка

Скопируйте `.env.example` в `.env` и задайте `LLM_API_KEY`, `LLM_MODEL` и при необходимости `LLM_BASE_URL`. Выберите модель с поддержкой Chat Completions, function calling и JSON output. После изменения настроек перезапустите backend.

По умолчанию endpoint — `https://api.openai.com/v1`; модель намеренно не выбирается за пользователя. Возможен совместимый провайдер. Ключ используется только backend и не попадает во frontend или ответы API. `.env` исключён из Git.

Supervisor выполняет ограниченный цикл выбора tools. В чате первый ответ должен запросить tool; затем модель может запросить дополнительные расчёты и вернуть JSON. `/analyze` получает уже проверенный результат и фиксирует объяснение на этом плане: модель не может заменить его другим расчётом. Числовые поля результата и `evidence` формирует сервер. В тексте модель использует ссылки вроде `{{e1.score.after}}`: сервер проверяет источник и подставляет число. Цифровые значения без подтверждённой ссылки отклоняются, даётся одна попытка исправления. Это проверяет происхождение чисел, но не доказывает правильность всей словесной интерпретации модели.

При отсутствии ключа, таймауте, ошибке провайдера или непрошедшем проверку ответе возвращается `available: false`. Результаты уже выполненных tools сохраняются. Шаблонный текст не выдаётся за ответ LLM.

Документация использованного протокола: [function calling](https://developers.openai.com/api/docs/guides/function-calling), [Chat Completions](https://developers.openai.com/api/reference/resources/chat), [JSON output](https://developers.openai.com/api/docs/guides/structured-outputs).

### Если `ai_configured: false`

Для семейства `gpt-5.6` клиент автоматически передаёт `reasoning_effort: "none"`: это позволяет использовать function tools через текущий Chat Completions API. Для остальных моделей этот параметр не добавляется. Ограничение описано в [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/migrate-to-responses).

`backend/main.py` загружает только корневой `.env` при импорте: путь вычисляется от самого файла, а не от рабочей директории терминала. `ai/agent.py` проверяет непустые `LLM_API_KEY` и `LLM_MODEL`; `LLM_BASE_URL` используется для запроса, но не участвует в этом флаге. Имена совпадают с `.env.example`.

После создания или изменения `.env` остановите прежний backend через Ctrl+C и запустите его снова. Не полагайтесь на `--reload` для отслеживания `.env`. Убедитесь, что порт обслуживает нужный процесс:

```powershell
Get-NetTCPConnection -LocalPort 8000 -State Listen | Select-Object OwningProcess
Invoke-RestMethod http://127.0.0.1:8000/api/health
```

Ожидается `{"status":"ok","ai_configured":true}`. `load_dotenv(..., override=False)` сохраняет переменные процесса, в том числе пустые: если `LLM_API_KEY` или `LLM_MODEL` уже заданы в окружении, исправьте их либо удалите из окружения запуска перед перезапуском. Файл автоматически их не заменяет.

`ai_configured: true` подтверждает наличие настроек, но не доступность провайдера или совместимость модели. Для проверки настоящего вызова:

```powershell
$body = @{message='Inspect the initial city state using inspect_city_state and explain its main problems.'} | ConvertTo-Json
$reply = Invoke-RestMethod http://127.0.0.1:8000/api/chat -Method Post -ContentType 'application/json' -Body $body -TimeoutSec 180
$reply | Select-Object available,summary,evidence
```

`available: true` означает, что ответ LLM прошёл проверку приложения. При HTTP-отказе в консоли backend появятся только boolean-флаги: `provider_response_received=True provider_http_ok=False` и категория отказа (`bad_request`, `unauthorized`, `forbidden`, `not_found`, `rate_or_quota_limited`, `server_error`). Это подтверждает получение HTTP-ответа провайдера; ключ, URL и тело ошибки не логируются. `bad_request=True` требует проверки совместимости модели с Chat Completions, function calling и JSON output. `available: false` само по себе не позволяет отличить ошибку сети от отклонённого ответа модели.

Тесты конфигурации используют фиктивный `.env` и изолированное окружение, без реального ключа и сетевых запросов:

```powershell
.venv/Scripts/python.exe -m pytest tests/test_llm_config.py tests/test_agent.py -q
```

## Архитектура и зоны ответственности

```text
data/city_data.json          # Снимок данных и правил из rules/
ai/
  data.py                   # Загрузка единого набора данных
  validator.py              # Все ограничения сценария
  scoring.py                # Районные оценки и Score
  simulator.py              # Лаги, эффекты, синергии, подробный результат
  optimizer.py              # Полный перебор, отсечения и кеш
  comparison.py             # Разницы между двумя рассчитанными планами
  tools.py                  # Пять JSON-инструментов
  agent.py                  # Один Supervisor и адаптер LLM API
  grounding.py              # Проверка ссылок на рассчитанные значения
  system_prompt.md          # Границы и формат ответа агента
backend/
  main.py                   # FastAPI и раздача frontend/dist
  schemas.py                # Модели расчётного ядра
  agent_schemas.py           # Модели поиска, чата и AI-ответа
frontend/                   # React, TypeScript, Vite, Tailwind CSS, Recharts
tests/                      # Ядро, поиск, tools, API, цикл Supervisor
examples/requests.http      # Запросы для ручной проверки
scripts/demo.py             # Воспроизводимые примеры A–E без ключа
```

Ручной режим: `Frontend → API → validator → simulator → результат → Supervisor → tools → объяснение`.

Советник: `User → Frontend → API → Supervisor → tool → validator / simulator / optimizer → Supervisor → API → Frontend`.

Tools: `inspect_city_state`, `validate_scenario`, `simulate_scenario`, `compare_scenarios`, `search_scenarios`. В них нет LLM-вызовов. История и результаты предыдущего плана передаются явно; сервер не хранит состояние сессий.

## Правила и расчёт

Источник значений — два исходных файла `rules/`. `data/city_data.json` содержит их структурированную копию. Исходники `rules/` и локальные промпты остаются в `.gitignore` по существующим настройкам; приложение от их наличия не зависит. Дополнительный тест сверяет копию с Markdown, если исходник доступен.

- Бюджет 100; ровно пять различных мероприятий; не более двух одного направления.
- Районная мера требует существующий район; у городской `district` равен `null` или отсутствует.
- M1/M3 запрещены всегда; M4/M7 и M5/M13 — только в одном районе.
- Реализованный эффект: `effect × (8 − lag) / 8`.
- Синергии применяются после обычных эффектов и не масштабируются лагом.
- После всех добавлений показатели ограничиваются диапазоном 0–100.
- `D_d = Σ weight_k × indicator_dk`; `D_avg = Σ population_share_d × D_d`.
- `Score = 0.7 × D_avg + 0.3 × min(D_d) − N_crit`.
- `N_crit` считает все пары «район × показатель» строго ниже 40. Значение 40 не критическое.
- Числа внутри ядра не округляются. Округление выполняется только при отображении.

Невалидный план возвращает `valid: false`, конкретные ошибки и бюджет, **без Score**. База без мероприятий рассчитывается отдельно и не считается допустимым пользовательским планом.

Подробный результат содержит изменения каждого района и показателя, критические значения, синергии, разложение изменения Score и эффекты мер. Эффекты отдельных мер указаны до общего clipping; это не независимые аддитивные вклады в итоговый Score.

## Оптимизатор

Перебирает комбинации пяти разных ID, сначала отсекает превышение бюджета, направления и глобальные конфликты; затем перебирает размещения и исключает местные конфликты. Расчёты районных поднаборов используют арифметику симулятора и кешируются. Полные результаты победителей повторно проходят основной валидатор и симулятор. API сообщает число допустимых кандидатов и `search.exhaustive: true`.

Цели поиска — продуктовые критерии ранжирования, они **не меняют формулу Score**:

| objective | Приоритеты по порядку |
|---|---|
| `max_score` | Максимальный Score, затем меньшая стоимость |
| `balanced` | Максимальная оценка худшего района, затем минимальный разрыв районов, затем Score и стоимость |
| `focus_district` | Максимальная оценка выбранного района, затем Score и стоимость |
| `budget_efficiency` | Максимальный прирост Score на единицу расходов, затем Score и стоимость |

Оставшиеся совпадения разрешаются стабильным порядком ID и районов. Допустим меньший бюджет от 0 до 100; если пяти допустимых мер не существует, вернётся пустой список с объяснением. `top_k`: от 1 до 10. Кеш относится к фиксированному датасету; после изменения данных нужен перезапуск или `clear_search_cache()`.

События и оптимизация после событий пока не реализованы. Будущее расширение должно передавать изменённое состояние явным аргументом и включать его в ключ кеша, сохраняя текущие правила исходного сценария.

## API

| Метод | URL | Назначение |
|---|---|---|
| GET | `/api/health` | Работоспособность и наличие настройки AI |
| GET | `/api/context` | Город, каталог, ограничения, рассчитанная база |
| POST | `/api/validate` | `{decisions: [...]}` — проверка, в том числе незавершённого выбора |
| POST | `/api/simulate` | `{decisions: [...]}` — проверка и расчёт |
| POST | `/api/search` | `{objective, budget_limit, focus_district, top_k}` |
| POST | `/api/compare` | `{scenario_a: [...], scenario_b: [...]}`; разницы B − A |
| POST | `/api/chat` | `{message, decisions?, previous_decisions?, history?}` |
| POST | `/api/analyze` | Полный SimulationResult; backend сверяет его и вызывает Supervisor |

Ошибки бизнес-правил возвращаются с HTTP 200 и `valid: false`; ошибки формата запроса — HTTP 422. Недоступность AI — HTTP 200 и `available: false`. JSON ошибок не содержит ключей или внутреннего ответа провайдера. Интерфейс не пересчитывает Score и эффекты.

## Проверки и demo

```powershell
.venv/Scripts/python.exe -m pytest -q
npm.cmd --prefix frontend run build
.venv/Scripts/python.exe -m scripts.demo
```

Тесты проверяют исходные формулы, все ограничения, три синергии, порог 40, clipping, неизменность данных, перестановки решений, поиск по всем целям, сравнение, API и настоящий цикл вызова tools с тестовым провайдером. Для оптимизатора есть независимый полный перебор малого бюджета. Внешний платный LLM API для тестов не нужен.

Браузерные тесты требуют запущенного backend на порту 8000. Vite запускается конфигурацией Playwright автоматически:

```powershell
cd frontend
npx.cmd playwright install chromium
npm.cmd run test:e2e
```

При наличии Microsoft Edge можно использовать его без загрузки Chromium: в том же терминале задайте `$env:PLAYWRIGHT_BROWSER_CHANNEL = 'msedge'` перед запуском тестов. В Linux/macOS эквивалент — `PLAYWRIGHT_BROWSER_CHANNEL=msedge npm run test:e2e`.

Браузерные проверки используют реальный backend для выбора, валидации, расчёта, сравнения и поиска. Только ответы `/analyze` и `/chat` подменяются контролируемыми ответами, чтобы тесты не расходовали ключ: проверяются недоступность AI и отображение успешного структурированного ответа с рассчитанными данными. Также проверяются очистка устаревшего результата, мобильная навигация, управление клавиатурой и отсутствие горизонтального переполнения. Скриншоты сохраняются в `frontend/test-results/`.

Сценарии A–E доступны в `examples/requests.http` и `python -m scripts.demo`:

1. **A:** M7, M8, M10 в Нуре; M12 по городу; M5 в Сарыарке. Стоимость 95, Score приблизительно 56.54, критических показателей нет.
2. **B:** заменить M12 на M13 в Нуре — бюджет 109, расчёт отклоняется.
3. **C:** «Найди лучший сценарий до бюджета 90» → `search_scenarios(max_score, 90)`.
4. **D:** «Улучши Нуру» → `search_scenarios(focus_district, focus_district=Нура)`.
5. **E:** сравнить исходный план с переносом M8 в Есиль: стоимость прежняя, Score снижается, в Нуре остаётся критический S2.

Для demo на минуту: покажите базу → загрузите пример → рассчитайте результат → перенесите поликлинику и сравните → откройте поиск до бюджета 90. Естественно-языковой выбор tools демонстрируется после настройки LLM; прямой поиск работает без ключа.
